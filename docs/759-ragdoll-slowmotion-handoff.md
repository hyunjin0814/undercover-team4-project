## 0. 한 줄 — 원인

**권위 피어의 프레임레이트가 물리 스텝 레이트(50Hz)보다 높으면 걸렸다.** (해결됨 — §3-1)

시체의 루트 추종(`TickCapsuleFollow` / `TickRootFollow`)이 **프레임마다** 뼈 리지드바디의
트랜스폼에 쓰는데, 물리는 50Hz로만 돈다. 스텝당 주입 횟수가 1을 넘으면 솔버가 관절 오차를
못 따라잡고, 몸은 안 내려가면서 뼈만 떤다.

- **60fps 호스트 → 스텝당 1.2회 주입 → 정상**
- **100fps 호스트 → 스텝당 2.0회 주입 → 슬로모션**

관측자의 fps는 무관하다. **호스트(권위)의 fps만 관계있다.**

**수정은 들어갔고 검증도 끝났다**(`95ed43ac`) — 2026-08-20 빌드 실측에서
**132~240fps 호스트 6판이 전부 정상**이었다. 240fps는 스텝당 4.8회 주입으로, 슬로모션을
재현하던 100fps(2.0회)보다 두 배 넘게 가혹한 조건이다. 근거는 §3-1-1.

### 이어받는 세션이 처음 할 일

1. **원인은 닫혔고 계측도 내렸다**(§6 — 지운 것이 아니라 주석이다). 남은 것은 §9뿐이다
2. 다시 재야 한다면 **§6의 판정 기준과 측정 프로토콜을 먼저 읽는다**
   (`권한=True` 줄로만 판정 · **죽고 3초는 시체를 건드리지 말 것** · 에디터로는 조건이 안 만들어진다)
3. 판단이 남은 것 둘: **원격 밧줄 격차 0.54m**(§3-1-2) · **§3-2 세 항목**

⚠ **§4를 읽지 않고 옛 가설로 되돌아가지 말 것.** 1·2판이 짚었던 `침투해소상한` ·
speculative CCD · 밧줄 스프링은 전부 근거와 함께 배제됐다.

## 2. 원인 — 실측

### 2-1. 호스트의 프레임레이트가 갈랐다

`vSync=1 · 상한=-1`이라 fps는 모니터 주사율을 그대로 따라간다.

| 머신 | 주사율 | 실측 fps | **호스트일 때** |
|---|---|---|---|
| **Player1** (8bPe) | **60.0Hz** | **60.3** | ✅ **정상** |
| **Player2** (njXg2) | 100.0Hz | 100.0~100.3 | ⚠ **슬로모션** |
| **Player3** (MLU20) | 100.0Hz | 100.3 | ⚠ **슬로모션** |

**관측자 fps는 무관하다** — 교차 대조가 양방향으로 성립한다:

- Player1은 **60.3fps인데** 100fps 호스트 방에서 슬로모션을 봤다 (골반낙차 0.24 / 0.25 / 0.22m)
- Player3은 **100.3fps인데** 60fps 호스트 방에서 정상을 봤다 (골반낙차 0.49~0.73m)

1판 로그의 아픈 세션도 호스트가 Player2였다 → **60fps 호스트 1대 정상 / 100fps 호스트 2대 재현.**

### 2-2. 권위측 지표 (권한=True)

| | 골반낙차 | 최고하강 | 관절오차곡선 | 뼈속도곡선 |
|---|---|---|---|---|
| **60fps 호스트** ×5 | 0.39~0.72m | **1.86~2.04 m/s** | 초반 22~33mm → **3.6~15mm로 수렴** | 0.4~1.8 → **0.01~0.5로 잦아듦** |
| **100fps 호스트** ×3 | **0.22~0.25m** | **0.28~0.73 m/s** | 12~80mm를 **오가며 수렴 안 함** | **1.79~7.20으로 끝까지 높음** |

`관절오차곡선` 원자료:

```
정상  #9 [12.85 8.48 12.35 3.63 3.63]   #8 [33.05 12.25 12.53 28.25 15.46]
      #7 [26.48 11.69 11.77 8.47 23.14] #9 [32.02 7.94 5.05 5.03 27.31]
슬로모 #10 [28.72 15.00 70.68 29.61 12.51] #9 [25.60 16.20 22.99 56.43 46.17]
      #8 [59.75 45.55 31.16 55.96 69.68]  ← 3초 뒤에 오히려 커진다
```

**정상은 수렴하고, 슬로모는 수렴하지 않는다.** 그동안 "몸이 안 내려간다"고 본 것은
솔버가 매 스텝 중력이 아니라 이 오차를 푸느라 낙하에 쓸 예산이 없었던 것이다.

### 2-3. 메커니즘

`Fixed Timestep = 0.02`(50Hz)인데, 루트 추종은 **프레임마다** 돈다:

| 어디 | 무엇을 |
|---|---|
| [PlayerRagdoll.cs:784](../Assets/Scripts/Player/View/PlayerRagdoll.cs:784) | `Update()` → `TickCapsuleFollow()` (권위 전용) |
| [PlayerRagdoll.cs:1735](../Assets/Scripts/Player/View/PlayerRagdoll.cs:1735) | `CapturePose()` → 루트 이동·회전 → `RestoreCapturedPose()` |
| [NpcRagdoll.cs:173](../Assets/Scripts/NPC/View/NpcRagdoll.cs:173) | `Update()` → `TickRootFollow()` — **같은 구조, 같은 버그** |

`RestoreCapturedPose()`는 뼈 11개에 `transform.SetPositionAndRotation`을 쓴다.

주석은 이것을 *"렌더 전용 — `m_AutoSyncTransforms = 0`이라 액터로 안 넘어간다"* 로 정당화하는데,
**그 전제가 틀렸다.** `autoSyncTransforms`가 0이어도 트랜스폼 쓰기는 **다음 시뮬레이션 스텝
직전에 PhysX로 flush된다** — 그 설정이 미루는 것은 *쿼리*(레이캐스트 등)가 보는 시점이지
시뮬레이션이 보는 시점이 아니다. 그리고 동적 바디의 트랜스폼에 쓰는 것은 PhysX에게
**텔레포트**여서 누적된 솔버·접촉 상태를 무효화한다.

왕복이 비트 단위로 정확하면 델타가 0이라 무해하지만, 잔차는 매 프레임 재주입된다:

| 호스트 fps | 스텝당 주입 | 결과 |
|---|---|---|
| 60 | 60/50 = **1.2회** | 솔버가 따라잡는다 → 오차 수렴 ✅ |
| 100 | 100/50 = **2.0회** | 솔버가 절반의 기회만 → 오차 발산 ❌ |

그리고 이 오차를 흡수할 장치가 하나도 없다 — 전 프리팹이
`AutoConfigureConnectedAnchor = 1` · `EnablePreprocessing = 0` · `EnableProjection = 0`이다(§4-B).

## 3. 고친 것

### 3-1. 본 수정 — 루트 추종을 물리 레이트에 묶었다 ✅ **검증 완료 (2026-08-20 빌드 실측)**

`TickCapsuleFollow` / `TickRootFollow`를 **`FixedUpdate`로 옮겼다.** 주입이 스텝당 항상 1회가 되어
**프레임레이트와 무관**해진다 — 144Hz 호스트가 들어와도 같다.

잃는 것이 없다 — 뼈는 `Interpolate = None`이라 어차피 50Hz로만 갱신되고, 루트가 따라가는 대상인
골반도 50Hz로만 움직인다. 루트만 100Hz로 도는 것이 애초에 의미가 없었다.

| 파일 | 변경 |
|---|---|
| `PlayerRagdoll.cs` | `Update`에서 `TickCapsuleFollow()` 제거 → 새 `FixedUpdate`로 (게이트: `Ragdoll` + `HasMoveAuthority`) |
| `PlayerRagdoll.cs` | `FollowBodyYaw()`의 `Time.deltaTime` → **`Time.fixedDeltaTime`** (지수 감쇠라 시간 기준이 바뀌면 감쇠 속도가 바뀐다) |
| `NpcRagdoll.cs` | `Update`에서 `TickRootFollow()` 제거 → 새 `FixedUpdate`로 (게이트에 `!m_settled` 포함 — 잠든 몸 건너뛰기를 유지) |
| `RagdollPoseStreamer.cs` | **`[DefaultExecutionOrder(100)]`** |

⚠ **스트리머 순서를 왜 박았나.** 루트 추종이 `FixedUpdate`로 내려오면서 스트리머의 자세 캡처와
**같은 페이즈**가 됐다. `MonoManager.asset`이 없어 순서가 미지정인데, **루트 회전이 뼈의 로컬 값을
바꾸고 스트리머가 보내는 것이 바로 그 로컬**이라 어느 쪽이 먼저 도느냐로 보내는 자세가 갈린다.
뒤로 박아 **이번 스텝의 루트**를 기준으로 뜨게 했다. (이번 버그와 같은 계열의 함정이라 미루지 않았다)

**남는 트레이드오프:** `FixedUpdate`는 스텝 *앞*이라 루트가 **직전 스텝의 골반**을 읽는다 —
20ms, 3m/s면 6cm. 루트는 NetworkTransform이 100ms로 보간하는 대리값이라 무시할 수준으로 봤다.
**실측에서 권위측 골반-루트 격차는 1~8cm로 예측대로였다.** 다만 원격에서는 최대 **0.54m**까지
벌어진 판이 있다(§3-1-2) — 판단이 필요해 §9에 남겼다.

#### 3-1-1. 검증 — 권위(호스트, 143.9Hz 모니터 / FullScreenWindow)

`vSync=1`이지만 전체화면 창 모드라 실제로는 걸리지 않아 **132.8~240.2fps**가 나왔다.
240fps는 **스텝당 4.8회 주입** — 슬로모션을 재현하던 100fps(2.0회)보다 두 배 넘게 가혹한 조건이다.

| # | 평균fps | 골반낙차 | 최고하강 | 관절오차곡선 | 뼈속도 끝 |
|---|---|---|---|---|---|
| #8-1 | 132.8 | 0.65m | 1.78 | 25.55 → 18.75 → 11.76 → 5.61 → **3.29** | 0.01 |
| #8-2 | 162.9 | 0.73m | 1.69 | 26.44 → 18.35 → 12.28 → 6.90 → **5.16** | 0.02 |
| #8-3 | 153.9 | 0.67m | 1.86 | 27.04 → 12.07 → 10.37 → 9.37 → **9.16** | 0.18 |
| #7-1 | 175.9 | 0.69m | 1.77 | 23.67 → 21.14 → 11.79 → 8.40 → **10.48** | 0.03 |
| #7-2 | **240.2** | 0.73m | 1.71 | 28.90 → 10.84 → 10.21 → 12.92 → **5.50** | 0.01 |
| #7-3 | 221.4 | 0.75m | 1.74 | 25.06 → 10.15 → 13.00 → 9.17 → **4.12** | 0.01 |

전부 `비율=1.00 · 클램프 없음`, 최장프레임 8~37ms.

- **관절오차가 6판 모두 단조 수렴한다** — 끝값 3.29~10.48mm.
  슬로모였을 때는 12~80mm를 오가며 3초 뒤 69.68mm였다(§2-2)
- **뼈속도가 0.01~0.18로 죽는다** — 슬로모는 끝까지 1.79~7.20
- 골반낙차·최고하강이 슬로모 구간(0.22~0.25m / 0.28~0.73m/s)과 **겹치지 않는다**

**fps를 240까지 올려도 지표가 흔들리지 않는다 = 프레임레이트 의존성이 실제로 끊겼다.**
이것이 이 수정이 주장한 바로 그것이고, §2-3의 메커니즘 설명을 실측이 지지한다.

에디터에서도 6판을 더 쟀는데(46~72fps) 전부 정상이었다. 다만 **에디터로는 조건을 못 만든다** —
클라이언트를 붙이면 fps가 50Hz 근처로 내려앉아 애초에 고장 구간이 아니다. 판정은 빌드로 한다.

#### 3-1-2. 원격(60Hz 클라)에서 본 것

- `재생배율 0.98~1.12` · 유실 0~1패킷 · 홀드 대부분 0% → **재생 정상**
- 원격이 본 골반낙차 0.67~0.74m로 권위측과 일치 → **원격도 같은 정상 낙하를 본다**
- ⚠ 밧줄 견인 중 **골반이동 vs 루트이동이 최대 0.54m**(5.87 vs 5.33) 벌어진 판이 있다.
  권위측 같은 구간은 1~8cm였다. #763 A-2 잔여인지 NetworkTransform 보간 지연인지 미판단

#### 3-1-3. 같이 확인된 것

- **A-1 소유권 이관 정상** — 클라 3회 사망에 `사망 1→0` / `복귀 0→1` 세 쌍이 모두 찍혔고
  `플레이어오브젝트유지=True`. (에디터 측정에서 이관 로그가 3회 중 1회만 찍힌 판이 있었는데
  빌드에서는 재현되지 않았다 — 에디터/MPPM 아티팩트로 본다)
- **밧줄 견인이 느리지 않다** — 권위측 1.5초에 2.5~6.9m. #759가 적었던 "견인도 느리다"는
  이미 느려진 몸을 끌어서였다는 §1의 판단과 맞는다

### 3-2. 같이 볼 것 (원인이 닫힌 뒤에도 남는 것)

- ~~**`RestoreCapturedPose`의 "렌더 전용" 주석을 고친다**~~ — 2026-08-20에 정정했다. 코드 세 곳
  (`PlayerRagdoll`의 `TickHoldPoseUntilStream`·`TickCapsuleFollow`, `NpcRagdoll.TickRootFollow`)과
  문서 두 곳(`npc-ragdoll.md` · `ragdoll.md`)이 같은 전제를 복제하고 있었다.
  ⚠ `NpcRagdoll`의 순간이동 주석("두 대입이 서로 더해지지 않는다")은 **맞는 설명이라 두었다** —
  거기서 문제 삼는 것은 "즉시" 넘어가지 않는다는 것이고, 그건 사실이다
- `AutoConfigureConnectedAnchor`를 끄고 앵커를 바인드 기준으로 한 번만 굽는다 — 진입 오차가
  40~85mm나 되는 것이 정상은 아니다(§4-A). 본 수정으로 증상이 사라져도 이 값은 남는다
- `EnablePreprocessing`을 켜 본다 — 공짜고, 오차 흡수력이 달라진다

### 3-3. 하지 말 것

- **프레임레이트를 물리 레이트에 맞춰 묶는 것**(`vSyncCount = 2` 등) — 증상은 사라지지만
  게임 전체를 50fps로 내리는 대가다. 원인은 fps가 높은 것이 아니라 **프레임에 물리를 쓰는 것**이다
- **`Fixed Timestep`을 0.01로 올리는 것** — 100fps는 구제되지만 144Hz에서 다시 깨지고
  물리 비용만 2배가 된다

## 4. 이전 판에서 뒤집힌 것 — 다시 그 길로 가지 말 것

| 주장 | 판 | 판정 | 근거 |
|---|---|---|---|
| "낙하가 자유낙하의 **6~7배** 느리다 = 증상" | 1판 | **무효** | 기준선이 틀렸다(서서 무너지는 몸은 자유낙하가 아니라 발을 축으로 도는 막대다). 게다가 그 느림은 **정상 세션에도 있다** |

| **B. `ContinuousSpeculative`가 미리 제동을 건다** | 2판 | **불필요** | 실험(`-ragdollDiscrete`) 미실행. §2가 fps로 전부 설명하므로 후순위. 프리팹 값은 여전히 speculative다 |

## 5. 별건으로 남는 회귀 — 캡슐 무시 재적용

`PlayerRagdoll.cs`의 `IgnoreOwnCapsule` 주석은 *"세 곳에서 다시 건다: 시체를 켜는 순간, 뼈를
다시 물리로 놓아줄 때, 캡슐이 꺼졌다 켜진 것이 관측될 때(Update)"* 라고 하는데:

- "뼈를 다시 물리로 놓아줄 때" → `a17b845d`에서 **삭제됨**
- "시체를 켜는 순간" → **B-2에서 시체 오브젝트가 없어져 소멸**

남은 것은 `Awake` · Update 폴러 · `PlayerRagdoll.SetControllerEnabled(true)` 셋뿐이고,
`PlayerTowedMotion`은 재적용이 **없는** `PlayerMovement.SetControllerEnabled`를 쓴다.
**주석이 스테일하고 방어가 두 칸 비었다** — 이 브랜치가 만든 회귀다. 슬로모션과는 무관하지만
고쳐야 한다.

## 6. 계측 사용법 (⚠ 지금은 트리에 없다 — 되살려야 쓴다)

⚠ **아래 계측은 2026-09-05에 트리에서 지웠다.** 2026-08-20에 주석으로 막아 뒀던 678줄(5개 파일 —
`PlayerRagdoll` · `RagdollPoseStreamer` · `RagdollRig` · `PlayerIncapacitation` · `PlayerTowedMotion`)이고,
§4-B 실험 스위치(`-ragdollDiscrete` · `Override Collision Detection`)도 함께 갔다.

**되살리는 법** — 지운 커밋을 찾아 그 파일들의 해당 블록을 되돌린다:

```bash
git log --oneline -S "DumpFallRate" -- Assets/Scripts/Player/View/PlayerRagdoll.Diagnostics.cs
```

되살린 뒤에는 프리팹에서 스위치를 켠다(`m_logFallRate` · `m_logRopePull`은 삭제 시점에 프리팹에
직렬화돼 있지 않았으므로 필드가 돌아오면 기본값 `false`에서 시작한다).

**아래 표와 판정 기준은 지우지 않는다** — 다시 잴 때 무엇을 어떻게 읽는지가 여기 있고, §9가 남긴
두 건(원격 밧줄 격차 · §3-2)을 재려면 이 계측이 출발점이다.

| 태그 | 어디서 | 무엇을 |
|---|---|---|
| `[리그물리]` | 사망 1회 | 질량·감쇠·중력·침투해소상한·솔버 · `충돌검출` · `자동앵커` · `진입관절오차` |
| `[낙하속도]` | 사망 후 3초 창 | `비율` · `평균fps` · **`낙하곡선`** · `최고하강` · **`관절오차곡선`** · **`뼈속도곡선`** |
| `[밧줄]` / `[밧줄추적]` | 견인 시작 / 1.5초 뒤 | `관절` · `끌림` · `견인곡선` · `최고속도` · `평균속도` |
| `[자세도착]` | **원격 전용**, 2초 창 | 패킷/유실/`재생배율`/`홀드` |
| `[래그돌대역폭]` | 권위, 2초 창 | 패킷 · Hz · 페이로드B · 초당KB |
| `[소유권]` | 서버, 사망/부활 | `오너 X→Y` · `플레이어오브젝트유지` |

### 판정 기준 (4판에서 실측으로 갱신)

| 보는 값 | 정상 | 고장 |
|---|---|---|
| **`평균=…fps`** (권위 로그) | — (수정 후로는 **무관**해졌다) | 수정 전엔 **50Hz의 2배 이상**이 원인이었다 |
| **`관절오차곡선`** | 수렴한다 (→ 한 자리 mm) | **수렴하지 않는다** |
| **`뼈속도곡선`** | 끝에서 0에 가까워진다 (0.01~0.5) | **끝까지 높다** (1.8~7.2) |
| `골반낙차` | 0.59~0.75m | **0.2~0.25m** |
| `최고하강` | **1.6~2.2 m/s** | **0.3~0.7 m/s** |
| `진입관절오차` | — | **판별 못 한다. 보지 말 것** |

`골반낙차`·`최고하강`의 정상 범위는 4판 빌드 6판(132~240fps)과 에디터 6판으로 넓혔다 —
3판이 적었던 `1.8~2.1 m/s`는 표본 5개짜리였고 실제로는 1.6대도 정상이다.

⚠ **판정은 `권한=True` 줄로만 한다.** 원격의 뼈는 키네마틱이라 `뼈속도곡선`이 항상 `0.00`이고
`관절오차곡선`은 상수로 굳는다. 원격 `최고하강`도 5.8~20.0m/s로 뜨는데 스냅샷 사이를 점프한
값일 뿐이다 — **원격 줄로는 아무것도 못 가른다.**

⚠ **재려면 죽고 3초는 시체를 건드리지 말 것.** 낙하 창(3초)과 밧줄 창(1.5초)이 겹치면
`관절오차곡선`·`뼈속도곡선`의 2s·3s 칸이 견인 속도로 오염돼 고장과 똑같은 모양이 된다
(4판 에디터 측정에서 실제로 겪었다: 뼈속도 3s가 4~7m/s로 튀었는데 원인은 밧줄이었다).

⚠ 실험용 스위치: `Override Collision Detection` / `Collision Detection` 인스펙터 필드와
실행 인자 `-ragdollDiscrete`(인스펙터를 이긴다). **§4-B가 후순위가 됐으므로 정리 대상이다.**

```bash
grep -E "리그물리|낙하속도|밧줄|자세도착|소유권" \
  "$USERPROFILE/AppData/LocalLow/DefaultCompany/undercover-team4-project/Player.log"
```

⚠ 빌드는 실행할 때마다 이전 `Player.log`를 `Player-prev.log`로 민다 — **두 번 더 돌리면 사라진다.**
측정이 끝나면 바로 딴 데로 복사할 것.
